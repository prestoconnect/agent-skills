# Skill evaluation, 2026-10-02

The five cases in `evals.json` were run once each with a baseline prompt and once with the Presto Pay skill. Results are qualitative: the agents share this user's Presto Pay memory, and no repeated runs were made. A successful agent exit does not establish that generated application code builds or is safe to deploy.

| Case | Baseline | With skill | Assessment |
| --- | --- | --- | --- |
| Python FastAPI full integration | SDK, raw webhook verification, queried status, event deduplication, and a unique fulfillment job | Same core behavior, with additional payment reference and status checks | Little separation. Both require dependencies, migration, a fulfillment worker, and staging validation. |
| Java Spring refund | Persists an idempotent refund attempt and provides an admin reconciliation endpoint | Persists the attempt and queries `refundDetails` immediately after an uncertain outcome | Skill improves timeout handling. Neither arm compiled because Spring dependencies were unavailable. Both leave the database migration to the app. |
| Go webhook fix | Uses a verifier abstraction but leaves SDK verification, status query, acknowledgement, and durable store behavior unfinished | Uses SDK `VerifyRequest`, `Query`, and `WriteAck`; offline Go tests passed | Clear SDK integration gain. Both leave atomic event deduplication and fulfillment to an unimplemented store because the fixture has no database layer. |
| Next.js checkout | Implements checkout, return query, raw webhook verification, and event deduplication; explicitly leaves durable fulfillment unfinished | Adds a unique fulfillment job in the same transaction as the paid transition | Clear fulfillment gain. Neither arm installed dependencies, built, applied the migration, or ran a staging payment. |
| PHP Laravel review | Finds the unsafe webhook and hand-written signing, but treats the SDK as possibly unavailable and leaves the return/webhook race implicit | Recommends the official SDK, queried status, raw verification, unique event IDs, and a retryable fulfillment job | Stronger review. The skill answer does not explicitly state HTTP 401 for invalid signatures or cover refund reconciliation, though the rubric requests them. |

The Go, Java, and Next.js runs have per-arm exit results in their `results.json` files. An earlier all-case run was interrupted after Python, so its outputs are available without a completed `results.json`. All five arms using the skill exited successfully. `python scripts/check_skills.py --offline` and `git diff --check` passed after the runs.

`trigger-evals.json` was reviewed as a prompt set but was not run through an agent skill router; these results measure task completion after explicitly supplying the skill, not automatic skill triggering.

## Evaluation limits and next changes

1. Add a real order store and migration to the Go fixture before scoring the atomic deduplication and fulfillment assertions. The current fixture cannot demonstrate those behaviors.
2. Keep manual review for transaction, retry, and fulfillment assertions. Text matches and successful agent exits do not prove concurrency safety.
3. Run the same cases in a clean agent environment without the user's Presto memory to measure skill value for a new integrator. These results describe this user's current environment.
4. Tighten the PHP review instruction or rubric so unobservable refund and checkout flows are marked as unverified, while requiring explicit HTTP 401 advice for an invalid webhook signature.
