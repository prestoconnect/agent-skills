# Skill evaluation, 2026-10-02

Evaluated against `presto-pay` as of 0.2.0, which guards webhook redeliveries on the order record.

## Trigger evaluation

`python scripts/run_trigger_evals.py` with Claude Code 2.1.287 and its default model (Sonnet 5.5), only this
plugin loaded, no user settings or MCP servers. Each of the 20 prompts in `trigger-evals.json` ran three times.

| Prompts | Expected | Result |
| --- | --- | --- |
| 12 Presto Pay tasks: checkout, webhook, refund, keys, error codes, go-live review, timeouts, several merchants | Load the skill | 36 of 36 runs loaded it |
| 8 near misses: Presto/Trino and prestodb, Stripe, Razorpay, iPay88, generic RSA/DER keys, integer refunds with Adyen, a CSS theme named "presto" | Don't load it | 0 of 24 runs loaded it |

20 of 20 prompts passed. The run cost $1.77.

## Task evaluation

`python scripts/run_evals.py` with the Codex CLI 0.160.0, its memories disabled, and the fixtures copied outside
this repository. Each case ran once without the skill (baseline) and once with it. Assertions are from
`evals.json` and were graded by reading the produced code.

| Case | Baseline | With skill | Notes |
| --- | --- | --- | --- |
| Python FastAPI full integration | 3/12 | 12/12 | The baseline invented an HMAC webhook secret, a checkout-sessions API and USD, read the return status from its own database, and had no fulfillment job. The skill arm used `AsyncPrestoPay`, raw-body `webhooks.verify`, `NotifyAck`, a status-guarded update and a unique, retryable fulfillment job. |
| Java Spring refund, unknown outcome | 5/7 | 6/7 | The fixture already depends on the SDK, so the baseline found its API. It sent the `mid` as `merchantRefNum`, which fails every call with `1106`. The skill arm sent `prestoMrn` and queried `refundDetails` immediately after an uncertain outcome. Both used a random `refundRefNum` keyed to an idempotency key instead of one derived from the order. |
| Go webhook fix | 2/7 | 7/7 | The baseline still decided on `EventCode` and replied with plain HTTP errors. The skill arm used `VerifyRequest`, 401 on `*prestopay.SignatureError`, `Payments.Query` and `WriteAck`. Its offline tests passed. |
| Next.js checkout | 2/7 | 7/7 | The baseline invented an HMAC header and a `/checkouts` endpoint and had no fulfillment job. The skill arm verified the `Request` with the SDK, queried on both callbacks, and committed the paid transition with one fulfillment job. |
| PHP Laravel review | 2/6 | 6/6 | The baseline found the forged-webhook and double-shipping risks but did not know the SDK, `query`, the 401 reply or the ack. The skill review covered every assertion, including CSRF exemption. |

## Limits

- One run per arm; results are indicative, not statistical.
- No arm installed dependencies, built the application, applied a migration or ran a staging payment. Only the
  Go skill arm ran tests.
- The fixtures have no real order store for Go and no database layer for most cases, so atomicity was judged from
  the code and store contracts, not exercised under concurrency.
- The Python and Java skill arms needed more than 15 minutes and were rerun with a 30-minute limit. The Go skill
  arm ran before the skill was isolated and read the local Go SDK checkout as well as the skill.
